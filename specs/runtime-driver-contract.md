# Runtime driver contract

Status: draft. Drafted in Phase 3 and stable after Phase 3 of the RFC-36 run plan.

This spec covers the workload spec, driver operations, isolation levels, and mount modes.

## Run 17 contract

The caller supplies a `StableId { host, local }` for each workload and session. Both components contain one to 64 ASCII letters, digits, `_`, or `-`. The host component specifies the authoritative host. The local component is unique within that host's workloads or sessions. The saved IDs remain the same after a daemon restart and never derive from a PID. Callers allocate and preserve these IDs because the prototype has no allocator or cross-host registry ([#82](https://github.com/tbhb-dev/agent-hypervisor/issues/82)).

`WorkloadSpec` contains the runtime (`host`, `seatbelt`, or `apple_container`), visible isolation (`none`, `seatbelt`, or `virtual_machine`), optional image, mounts with read-only or read-write modes, environment pairs, credential references, network policy (`host`, `deny`, or `isolated`), optional memory and CPU limits, and host workspace and cache paths. The shell canonicalizes both paths before saving a workload. It gives each host session `WORKSPACE_DIR` and `CACHE_DIR` with those physical paths, overriding the session's values for those names. The host driver accepts only `host` with `none` isolation, host network, no image, mounts, credential references, or resource limits. Unsupported controls fail before the shim starts. A host process has no effective isolation boundary.

The driver operations are `create`, `start`, `stop`, `destroy`, `spawn_session`, `list_sessions`, `stats`, and `events`. `create` writes private workload metadata. `start` creates one detached shim process and confirms the expected workload ID on its private control socket. `spawn_session` starts the merged PTY and session actor inside that shim and returns a per-session terminal channel socket. `list_sessions` returns held stable IDs. `stats` returns the held session count, while `shim_pid` exposes the PID for supervision diagnostics from the same control reply. `events` returns the shim's in-memory workload and session creation events. Later lifecycle events are tracked in [#83](https://github.com/tbhb-dev/agent-hypervisor/issues/83). `stop` asks the shim to close and join its sessions before the shim exits. `destroy` removes stopped metadata. The Phase 4 control API and durable event log are tracked in [#87](https://github.com/tbhb-dev/agent-hypervisor/issues/87).

On daemon startup, the host driver reads the private metadata directory and probes each deterministic shim socket. A response containing the saved stable ID gives running status. A failed probe gives stopped status without automatically restarting the shim. A later explicit `start` removes a stale socket pathname after finding that no process answers it. Reconnection rebuilds the workload table without merging stores or replaying session commands. The shim holds PTY and emulator state. The daemon can exit while the session remains attachable at its channel socket.

Run 17 provisionally places shim creation, reconnection, and stop in the privileged host daemon pending REQ-128's RFC-45 daemon/proxy decision ([#74](https://github.com/tbhb-dev/agent-hypervisor/issues/74)). The proxy would still have no shim ownership or authorization authority. Run 18 adds launchd registration after operator approval. This run detaches a shim with `setsid()` and does not install or register a launch agent. A detached shim can keep running after the daemon exits. Without launchd, the driver cannot restart a crashed shim or recover its exit status after daemon death ([#85](https://github.com/tbhb-dev/agent-hypervisor/issues/85)). Its behavior under a Linux systemd cgroup is untested ([#86](https://github.com/tbhb-dev/agent-hypervisor/issues/86)).

Host stop asks the merged holder to hang up and then kill each PTY process group. A descendant that escapes its group with `setsid()` can keep running after host stop ([#47](https://github.com/tbhb-dev/agent-hypervisor/issues/47)). The host user boundary limits containment here. Session sockets remain direct local transports from run 16. The later proxy and authorization phases must constrain who can use them ([#76](https://github.com/tbhb-dev/agent-hypervisor/issues/76)).

The shim serves control connections concurrently and limits each request to 1 MiB and two seconds from connection, then drops a malformed, oversized, silent, or slow connection without ending the shim or its sessions. A silent or slow connection does not delay another control request. A stop request closes every held session and waits for its process group to end before removing the shim socket. Shim-owned sessions do not retain their exited state during stop. This avoids the holder's default 60-second retention delay while keeping the two-second group-kill grace.

## Run 18 launchd supervision

`HostDriver::open_launchd` registers each shim as a launchd job in the user's `gui/<uid>` domain, and `open` keeps run 17's detached shim for Linux and CI. The core derives the job label `<prefix>.<host>.<local>` from the stable ID, never from a PID. Product jobs use the prefix `dev.tbhb.hypervisor.shim`, and tests use `dev.tbhb.hypervisor.test.` prefixes. `start` writes a private property list beside the workload metadata and loads it with `launchctl bootstrap gui/<uid> <plist>`. Because the plist never goes under `~/Library/LaunchAgents`, launchd does not load the job at login or after a reboot ([#95](https://github.com/tbhb-dev/agent-hypervisor/issues/95)). Its `KeepAlive` dictionary sets `SuccessfulExit` to false, so launchd restarts a crashed shim after `ThrottleInterval` seconds but not a shim that exited after a stop request. A loaded job whose shim does not answer is booted out and bootstrapped again. `stop` and `destroy` boot the job out after the shim exits. The driver reads only the exit status of `launchctl print`, whose output is not an API.

Adoption on startup still proves identity over each shim's control socket, because launchd tells the daemon nothing. The driver removes a stale socket before its own `start`, so a shim that finds one was restarted unattended. That shim records a `shim_restarted_after_unclean_exit` event, and the daemon reports it as `Restarted` rather than `Running`. The PTYs closed with the crashed shim. Its sessions ended and are not re-adopted ([#93](https://github.com/tbhb-dev/agent-hypervisor/issues/93)). The crashed shim's exit status is not recovered ([#85](https://github.com/tbhb-dev/agent-hypervisor/issues/85)).

Upgrades replace the daemon, not running shims. Each job's plist stores the shim binary path it started with. Upgrading the daemon installs a new shim at a new path and leaves running jobs on their pinned binary, and a crash restart reruns that binary. New shim versions apply when a workload next starts, which ends its sessions ([#93](https://github.com/tbhb-dev/agent-hypervisor/issues/93)). The new daemon must speak the old shim's control protocol, and that protocol has no version yet ([#94](https://github.com/tbhb-dev/agent-hypervisor/issues/94)).

Test labels start with `dev.tbhb.hypervisor.test.owner-<pid>-`, which records the PID of the test process that registered the job. Before a test registers a job, it boots out every test job whose owner is dead, using the core's `test_jobs` and `sweep_targets` decisions. A SIGTERM handler boots out the process's own jobs before exit, and `JobGuard` covers return and panic. `tests/check-launchd-jobs.sh` boots out and fails on any recorded job left loaded after the suite. Child test runs prove the SIGKILL and SIGTERM paths. A test run killed with SIGKILL doesn't clean up. Its job remains loaded and its shim keeps running until the next launchd test run's sweep boots the job out. A reused owner PID hides a leaked job from the sweep until that PID exits. An attended `start` after a dead shim is adopted as `Running`, and a `start` over a loaded job whose shim is stopped replaces the job. On macOS 26.5.1, `launchctl bootstrap` of a loaded label fails with status 5. `launchctl print` reports a jetsam thread limit of 32 for these jobs, which may cap sessions per shim ([#96](https://github.com/tbhb-dev/agent-hypervisor/issues/96)).

Three more macOS-only tests cover survival. A separate daemon process adopts a launchd shim and its session. A daemon binary swapped by rename adopts the same shim PID, whose job still names its pinned program. A shim killed with `SIGKILL` is restarted by launchd and reported as restarted with no sessions.

The launchd integration tests require `launchctl bootstrap`, which returns status 5 inside the Codex worker sandbox. `mise run check` keeps them in the test binary as visibly ignored cases and prints a notice that they did not run. `mise run check:host` runs all cases, including the child-run cleanup cases, on an unsandboxed macOS host and checks for surviving fixture groups and jobs. Before merge, the reviewer records a passing host run at the PR's current head SHA and names the host. The Linux CI `check` cannot establish launchd behavior. An unavailable or failing host run blocks merge ([#107](https://github.com/tbhb-dev/agent-hypervisor/issues/107)).

## Run 19 Seatbelt driver

Run 19 builds source lines 177 and 178 and proposal line 116 at vault commit `331d791c3704663135a8899cb44867714e9dc800`. The host shim also serves `seatbelt` workloads. `validate_workload` dispatches on the runtime and refuses `apple_container`. A seatbelt workload needs `seatbelt` isolation, no image, credential references, or resource limits, and `host` or `deny` network. `isolated` is refused ([#113](https://github.com/tbhb-dev/agent-hypervisor/issues/113)). A mount specifies one absolute path, with its source equal to its target, because Seatbelt grants access and cannot remap. `create` canonicalizes mount paths, since Seatbelt matches physical paths such as `/private/tmp`.

The shim runs unsandboxed with run 17's start, stop, and adoption behavior. Each session runs as `/usr/bin/sandbox-exec -p <profile> -- <command> <args>`. `sandbox-exec` runs the command in its own process, so the PTY process group and stop behave as on the host driver. `hypervisor_core::seatbelt::profile` generates the profile text from the workload spec, the user's home, and the driver root. The profile starts from `(allow default)`, then applies these path rules in order, and the last matching rule decides:

1. Deny `file-write*` everywhere.
2. Allow writes below `/dev`, the workspace, the cache, and read-write mounts.
3. Deny `file-read-data` below the home directory.
4. Allow reads of the workspace, the cache, and every mount.
5. Deny reads and writes of `.ssh`, `.gnupg`, `.aws`, `.netrc`, `.config/gh`, `.codex/auth.json`, and `Library/Keychains` under home, and of the driver root, even when a mount covers them.
6. Deny Unix socket connections everywhere, then allow them below the workspace and the cache. With `host` network, also allow `/private/var/run/mDNSResponder`, the system resolver, because name lookups fail without it. Last, deny connections into the driver root.

Rule 6 blocks connections to the shim control socket, other terminal sockets, the user's SSH agent, the 1Password agent under `~/Library/Group Containers`, and the launchd ssh-agent socket under `/private/tmp/com.apple.launchd.*`. The shim also drops `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `SSH_ASKPASS`, `GPG_AGENT_INFO`, and `DBUS_SESSION_BUS_ADDRESS` from a seatbelt session's environment. The profile adds `(deny network*)` for `deny` network. It denies the four Keychain mach services from RFC-37 run 9, plus `lsopen` and `appleevent-send`, so a session cannot open a Keychain prompt or a GUI app. The core's `allowed` function evaluates the same rules with Seatbelt's `subpath` and last-match semantics. Property tests use it to show that any mounts leave secret paths and the driver root denied and that writes outside the write roots are denied. Another property shows Unix sockets outside the workspace and cache are unreachable. The base allows reads outside home and every other mach service, which differs from RFC-37 run 9's deny-default recommendation ([#112](https://github.com/tbhb-dev/agent-hypervisor/issues/112)). Until #112, a session may execute any binary it can read, such as `/usr/bin/perl` or `/usr/bin/curl`. Only setuid binaries fail, and no cell in the matrix below should be read as an exec restriction. Sessions can also read file metadata under home.

`crates/hypervisord/tests/seatbelt_driver.rs` covers the session boundary and the lifecycle on macOS only ([#115](https://github.com/tbhb-dev/agent-hypervisor/issues/115)). Seatbelt does not nest, so `mise run check` lists these tests as ignored, and `mise run check:host` runs them with the launchd tests on an unsandboxed macOS host before merge. A session writes in its workspace but not outside it. It cannot read the driver root or list home, and with `deny` network, `nc` to a loopback listener fails. With `host` network, a session cannot connect to a stand-in agent socket in a temporary directory outside its workspace, though a socket in the workspace accepts its connection. The session does not see the `SSH_AUTH_SOCK` passed to it. Stop ends the sandboxed process group, and a new daemon reports the running seatbelt shim and its session as `Running`.

## Run 20 CLI plan

The pure `hypervisor_core::container` plan validates an Apple container workload with virtual-machine isolation, an image, a bounded stable name, and absolute mount paths. It rejects host networking, credential references, paths that can change the meaning of the CLI mount syntax, and mounts beneath driver-owned guest targets. The planned `container run` uses one detached VM per workspace with `--init`, a bind-mounted `/workspace`, a named cache volume at `/cache`, a mounted agent executable and metadata file, and a published agent socket. It sets `--network none` for both `deny` and `isolated` requests. An optional broker socket mount at `/run/broker.sock` uses `--volume`, since run 1 found that `--mount type=bind` refused a Unix socket file. The current stage has golden and property tests for the arguments. Runtime behavior is untested until `mise run check:host` runs.

The no-network choice follows [RFC-37 run 8](https://github.com/tbhb-dev/agent-orchestration-poc.internal/blob/55dcdf93f72e50a1916a67b8a2a8ef9d4f741141/wiki/proposals/2026-10-07T2010Z-RFC-37-egress-credential-identity-spikes/findings/r8-container-egress.md) and [run 31](https://github.com/tbhb-dev/agent-orchestration-poc.internal/blob/55dcdf93f72e50a1916a67b8a2a8ef9d4f741141/wiki/proposals/2026-10-07T2010Z-RFC-37-egress-credential-identity-spikes/findings/r31-tailnet-lan-peers.md). An `--internal` network still exposed host services and DNS. `--network none` left only loopback in run 8. This design gives each workspace its own VM network namespace. It does not create a named bridge network.

The broker socket is the workspace's only way out, so the listener behind it judges every request on its own. To judge is to compare the destination host with the workspace's allowlist. The host is lowercased and otherwise compared exactly, so a name with a trailing dot doesn't match and gets `403`. The allowlist matches hosts only, as egress entries in the authorization model name an exact host and no port, so an allowed host is allowed on any port. The broker checks the port only for agreement between the request target and the `Host` header. A missing port defaults to 443 for CONNECT and `https` or 80 for `http`. If the two ports differ, the request gets `400`. The broker judges each CONNECT tunnel once, from its request target, because after the `200` reply the tunnel's bytes go only to that host and port. It judges each plain HTTP request from its absolute-form authority, or from its `Host` header when the target is in origin form. A plain connection either has each request judged, or the broker accepts one request per connection and sends `Connection: close` both ways.

A denial answers `403` for a destination off the allowlist and `400` for a request that breaks a rule below, with `501` for `Transfer-Encoding` without `Content-Length`. The exceptions are a dropped CONNECT after a plain request, a nested CONNECT, and non-HTTP bytes, which don't get a response, as their rules say. In every case the broker closes the connection and forwards nothing upstream. A test can hit each of these rules:

- Pipelining: the broker never forwards bytes that follow the first framed request unless it has judged them as a new request. This holds for bytes that arrive before the first response too.
- Request smuggling: ambiguous framing is refused, never forwarded or reinterpreted. That covers `Content-Length` together with `Transfer-Encoding`, duplicate or differing `Content-Length` values, a `Transfer-Encoding` whose final coding isn't `chunked`, and obs-fold or whitespace before a header colon.
- Upgrade: the broker refuses a plain request with an `Upgrade` header (WebSocket or `h2c`), or it treats the `101` reply as a new tunnel and judges it like CONNECT. The connection never becomes an unjudged byte pipe.
- Mismatched host: if the `Host` header names a different host or port than the absolute-form authority, the request gets `400`.
- CONNECT after a plain request on one connection is dropped, and nothing is forwarded. The connection closes after the one plain request, so the CONNECT is never judged there. A CONNECT the client resends on a new connection is judged like any other.
- Nested CONNECT: when a tunnel's first client bytes are a plaintext `CONNECT`, the broker closes both sides and forwards none of them. The `200` has already gone out, so this denial is a close, not a `403`.
- Bytes that aren't HTTP, such as the raw TLS ClientHello Claude Code sent into the socket in RFC-37 run 8, close the connection without any response, not a `400`, and nothing is forwarded.

RFC-37 run 11 found that `sandbox-runtime` 0.0.79 reuses one proxy connection across hosts. Run 8's stand-in broker judged only the first request on a connection, so it forwarded a later request to a host off its allowlist ([internal #72](https://github.com/tbhb-dev/agent-orchestration-poc.internal/issues/72)). The reference stand-in broker is at [commit `9643e36f`](https://github.com/tbhb-dev/agent-orchestration-poc.internal/blob/9643e36f6028923e085d824096d47de5dcab79d0/wiki/proposals/2026-10-07T2010Z-RFC-37-egress-credential-identity-spikes/findings/r8-container-egress.md#later-finding-the-broker-judged-only-the-first-request-on-a-connection). It refuses `Upgrade`, a plaintext CONNECT as a tunnel's first bytes, a mismatched `Host`, duplicate `Content-Length`, `Content-Length` with `Transfer-Encoding`, and obs-fold, and it never forwards bytes after one framed request. Its socket tests check what the upstream received in each of those cases. They also cover a second request on one connection, pipelining, and a CONNECT after a plain request. The findings section linked above holds the reproduction.

Residual risk, recorded in those findings as inference: the broker checks only a tunnel's opening bytes, and it can't parse a tunnel. An inner CONNECT later in an opaque tunnel is forwarded to the allowed endpoint, and so are any request inside TLS and `Host` or SNI routing at a shared front end such as a CDN. An allowed host on any port widens this, since a port is never judged. So the allowlist must not list forward proxies or open relays. It may list a destination behind a shared front end only if every site that front end routes to is acceptable, until a broker that decrypts the tunnel's TLS can judge inner requests. This repository has no broker yet. [Issue #131](https://github.com/tbhb-dev/agent-hypervisor/issues/131) tracks the tests the broker needs before it merges.

## Run 20 CLI lifecycle

`ContainerDriver::create` canonicalizes host paths and writes a private host spec with a guest-path copy. It creates a named cache volume. The guest sees `/workspace` from the host bind mount and `/cache` from that volume. The canonical host `cache_dir` remains registry metadata but does not back `/cache` in this driver. `start` runs exactly one detached container for the workspace name, then asks the published agent socket for its stable identity. A failed start attempts to remove any container it created. `stop` requests `container stop --time 0` and forces deletion if stop fails. It removes the terminal proxies. `destroy` deletes the volume and metadata after the container stops. The driver uses the `none` network without creating a named network.

`create` and `start` refuse a workspace with a root `.git` entry, including a directory, gitfile, or symlink. The bind mount otherwise gives a guest write access to host Git settings, which [RFC-39 run 5](https://github.com/tbhb-dev/agent-orchestration-poc.internal/blob/69dc14c7a0e864329c4f8a4301e8688b67363fd4/wiki/proposals/2026-10-07T2052Z-RFC-39-filesystem-spikes/findings/r5-git-layout.md#L14) showed can cause host Git to execute guest-written code. Because a `.git` entry can appear after the VM starts, host Git must stay away from this writable workspace while it is mounted. [Issue #129](https://github.com/tbhb-dev/agent-hypervisor/issues/129) tracks the safe Git layout and runtime boundary.

`spawn_session` sends the session request to the guest agent and exposes the returned terminal as a private host Unix socket. Each connection forwards the existing terminal channel bytes to the guest. A new daemon instance accepts a running container only after the agent replies with the saved workload ID. It then lists sessions and recreates their local terminal sockets. Dropping the driver leaves the VM running, as dropping `HostDriver` leaves its shim running. The guest executable must be a Linux arm64 binary. `mise run guest:build` produces one at `target/aarch64-unknown-linux-musl/debug/host-shim`.

The macOS-only `container_driver` test creates one VM with two CPUs, a 512 MiB memory limit, and a cache volume with the CLI's default sparse 512 GiB disk size ([Apple container 1.4.1 volume reference](https://github.com/apple/container/blob/1.4.1/docs/volumes.md)). It checks a writer UID, a reviewer UID, the reviewer's read-only workspace and Git lock setting, a terminal proxy, reconnection, no default route, and cleanup. The temporary host workspace has mode 0777 so the guest UIDs can write during the test. Access to a private 0700 host workspace remains untested and is tracked by [issue #128](https://github.com/tbhb-dev/agent-hypervisor/issues/128). The test runs only through `mise run check:host` on an unsandboxed Mac. It prints the disk allocation reported by `container inspect` and the cache volume size from `container volume inspect`. The reviewer must record the current SHA and test result, then confirm cleanup separately. The sandbox returns `Operation not permitted` for `container ls --all`. These behaviors remain untested here. The test uses an Alpine image for shell probes. Harness images and actual Claude Code or Codex behavior remain untested in this run.
